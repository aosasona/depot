# ADR 0021: Configure GitHub Apps through the manifest flow

## Status

Accepted

## Context

Repository discovery already used a GitHub App, but creating that App required
manually entering URLs and permissions in GitHub, copying a generated PEM key,
writing a webhook secret to the Depot VM, editing TOML, and restarting both
services. This kept the primary GitHub-first project flow hidden from operators.

## Decision

Administrators can initiate GitHub's App Manifest flow from the new-project
wizard. Depot supplies the exact public callback, setup, webhook, contents-read
permission, and push-event subscription. After GitHub returns a one-time code,
the authenticated browser asks Depot to exchange it for the generated App
identity, PEM key, and webhook secret.

The PEM key and webhook secret are encrypted with Depot's existing external
master key and authenticated with distinct fixed contexts before SQLite
persistence. They are never returned to the browser or logs. API requests and
worker jobs resolve the stored configuration dynamically, so setup does not
require a service restart. File/TOML configuration remains a supported fallback
for existing installations.

The front-channel manifest `state` is generated by the browser and checked
against session storage. The credential exchange additionally requires an
active administrator session and the session-bound CSRF header. GitHub's
one-time conversion code remains bounded and is sent only to GitHub's fixed API
origin.

## Consequences

- A fresh administrator can create, install, and connect a least-privilege
  GitHub App entirely from Depot's UI.
- Routine project creation can browse public and private repositories without
  manually entering Git URLs.
- The master key must remain available to both API and worker processes, as it
  already is for project secrets.
